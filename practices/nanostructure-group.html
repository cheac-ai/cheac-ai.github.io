Why a group file?

The CHEAC standard for AI agent instructions is deliberately general. It covers data handling and scientific integrity, which apply to everyone at CHEAC. Within the Nanostructure group, we also share conventions for code, git, and figures. An agent should follow those without being told again in every session.

This page publishes the instruction file I use day to day, so that everyone in the group can start from the same rules. Copy it, change About me to your own field, and adapt the rest to your work.

How it differs from the CHEAC standard

Kept from the CHEAC standard

  • About me, filled in for our field.
  • Scientific integrity: no invented data or references, checkable sources, explicit units and assumptions.
  • The two core Research data rules: raw data is read-only, and processed data goes in a separate folder.
  • Approval before copying data off your machine or touching credentials, and a summary at the end of each task.

Added for the group

  • Honest figures. Claude must report any shift or offset it applies, and must never shift data along an axis that reports a quantity.
  • Git workflow. We use a forking workflow: origin is your fork, upstream is the group repository. You always branch from an up-to-date main, never commit to main directly, and use conventional commit messages (feat:, fix:, …). The git workflow post uses a simpler single-remote setup and is the place to learn the basics first.
  • News files. Every pull request comes with a news entry created with package add news.
  • Conda environments. Packages come from conda-forge, installed from the project’s requirements/ files (see Switch to conda-forge in Onboarding).
  • pre-commit and code style. flake8, NumPy-style docstrings, pathlib for paths, and compact code.
  • Figure style. Nature figure widths, colour-blind-friendly colours, the Billinge colours for PDF and Rietveld fits, and standard font sizes.

Left out

The CHEAC standard’s rules on dataset READMEs, installing packages, and open file formats aren’t in this file. If you want them, copy them over from the CHEAC standard.

The group file is also much longer than the CHEAC standard, and the code and figure sections only matter when Claude writes code or makes figures. They’re good candidates to move into a skill later.

How to use it

  1. Open your global instruction file, ~/.claude/CLAUDE.md for Claude Code (see What goes in an instruction file). Create it if it doesn’t exist.
  2. Paste in the file below and change About me to your own field and interests.
  3. Keep project details (what the project is, where its data lives) in a CLAUDE.md or AGENTS.md in the project folder, not here.
  4. Start a new session and ask: “Summarise the instructions you have been given.” Claude should list the rules back to you.

The git and pre-commit sections say applies only to projects that contain git repos, so they don’t get in the way when you work in a plain data folder.

The group instruction file

Copy the block below with the copy button in its top right corner.

# Agent instructions — Nanostructure Group (v1, October 2026)

## About me
- I am a researcher at the Center for High Entropy Alloy Catalysis (CHEAC), University of Copenhagen. My field: Chemistry, materials science, x-ray scattering. I am particularly interested in the nanostructure problem, structure--property relations, and defects and disorder in materials.


## Research data (follows the CHEAC Data Management Plan)
- Never modify, move, rename, or delete raw data: instrument output,
  simulation output, or files from external facilities. Treat them as
  read-only.
- Write processed data to a separate, clearly labelled folder
  (e.g. `processed/`), never next to the raw file under a similar name.
-  Ask for approval before before deleting or overwriting files.


## Scientific integrity
- Never invent data, numbers, references, or DOIs. If you do not know,
  say so.
- Every literature claim needs a source I can check. Give the DOI or URL.
- State units, uncertainties, and assumptions explicitly.
- When a result looks surprising, say so and suggest how to check it
  before I rely on it.
- When making figures, always report to me when you apply any shifts and offsets. As a general rule:
    - never shift anything along an axis that reports a quantity;
    - horizontal jitter or offsets on categorical axes are fine;
    - constant offsets of stacked curves are fine.


## Git Workflow (applies only to projects that contain git repos)

If the project folder contains a cloned git repository, explicitly ask if I intend to commit and push changes to the remote, or if I am not actively contributing to the remote repo. In case of the latter, ask if the git tracking should be removed.

I use a **forking workflow**:
- `origin` = my personal fork
- `upstream` = canonical/group repo

### Branch discipline — ALWAYS follow this sequence:
1. `git checkout main`
2. `git pull upstream main`
3. `git checkout -b <feature-branch>` — keep branch names short, just enough to recall the topic (e.g. `fix-testpaths`, `feat-build-cli`, not `fix-configure-pytest-testpaths-to-prevent-collection`)
4. Work and commit on the feature branch
5. Push to `origin` with `git push -u origin <branch>` on first push (sets upstream tracking so subsequent pushes need only `git push`)
6. Open a PR from the fork into `upstream` (only when asked)

**Never commit directly to `main`.** Never branch off an existing branch unless explicitly instructed.

### Commit messages
Use conventional prefixes: `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`

## News Files (applies to all projects)

Every PR requires a news file. Create one immediately after branching using:

```bash
package add news <flag> "Brief user-facing summary (under 72 chars)"
```

Flags (mutually exclusive):
- `-a` — Added (new feature)
- `-c` — Changed (modification to existing feature)
- `-d` — Deprecated
- `-r` — Removed
- `-f` — Fixed (bug fix)
- `-s` — Security
- `-n` — No-news needed (trivial change; reviewer decides if that's appropriate)

The command reads the current branch name and creates `news/<branch-name>.rst`.
Stage and commit the news file along with the rest of the PR work.

For no-news, use: `package add news -n "reason why no news is needed"`

## Conda Environment Setup (applies to all projects)

When setting up or initialising a conda env for a project, install from **conda-forge** everything in:
- `requirements/conda.txt` (project-level)
- `requirements/tests.txt` (project-level)
- `~/dev.txt` (global, in the user's home directory)

```bash
conda install -n <env> -c conda-forge --file requirements/conda.txt --file requirements/tests.txt --file ~/dev.txt
```

Only fall back to pip for packages not on conda-forge.

## pre-commit (applies only to projects that contain git repos)

Run `pre-commit install` at the start of any project so hooks run automatically on every commit.

Never use `git commit --no-verify` (`-n`) except temporarily when auto-fixes need to be committed mid-cleanup. Once all issues are resolved, always commit without `-n`.

## Code Style (group standards)

### Style guide enforcement
Use flake8 (max line 79, ignore E203)

### Docstrings
All docstrings must be in **NumPy format** (Parameters, Returns, etc. sections).

### Docstring parameter descriptions
All parameter descriptions in NumPy docstrings must begin with **"The"**.

### argparse help strings
Write argparse `help=` and `description=` strings to be as informative as possible. Include examples where helpful. Do **not** force them to start with "The" — some inputs are actions where that makes no sense.

### Exception message
All exception messages must include concise information about 'what is wrong' and 'how to fix it' when they are raised.

### File paths
Always use `pathlib.Path` for file and directory paths. Avoid `os.path`, string concatenation, or `open()` with raw strings.

### Code density and comments
- Prefer self-documenting code over explanatory comments. If a comment is needed, the code may need renaming.
- Only add blank lines where they semantically separate blocks with very different purposes. Do not add blank lines for visual breathing room.
- Follow PEP 8, but where PEP 8 is silent, lean compact. Three lines of clear code is better than the same code padded to six.
- This applies everywhere: source code, tests, config files.

## Actions that need my approval
- Copying data off my machine (SFTP, cloud upload, git push).
- Anything involving passwords, keys, or login details. Never print them.

## When you finish a task
- Summarise what you changed, which files you created, and anything I
  should check by hand.


## Figure making
- When asked to make a figure, if not specifically instructed otherwise, always use these general style guidelines:

- **Letters**: We want to use a coherent style sheet for publication ready figures. Avoid putting too much text outside of panels. Use bold letters for labeling panels such as **a**, **b**, **c**, etc. Use Arial if available.

- **Syntax**: Start every string with capitalized letters. Format labels as $G(r) \, / \, \mathrm{\AA}^{-2}$, $I(Q) \, / \, \mathrm{\AA}^{-1}$, and $r \, / \, \mathrm{\AA}$

- **Nature colors**: typically, we will use blue and verm in combinations with black and gray shaded lines in figures. Below are the codes needed to define the color shades.

```python
orange = (230/255, 159/255, 0/255)
skyblue = (86/255, 180/255, 233/255)
green = (0/255, 158/255, 115/255)
yellow = (240/255, 228/255, 66/255)
blue = (0/255, 114/255, 178/255)
verm = (213/255, 94/255, 0/255)
purple = (204/255, 121/255, 167/255)
red = '#be1818'
```

- For plotting a standard PDF or Rietveld refinement fit, use the billinge colors: bg_blue for data (circles), bg_red for the fit (line), and bg_green for the difference curve (line with negative offset). Add a dashed offset zeroline on top of the difference curve.

```python
bg_blue = '#0B3C5D'
bg_red = '#B82601'
bg_green = '#1c6b0a'
```

- For sequential colors, use:

```python
plot_color_gradients('Sequential',['Greys', 'Purples', 'Blues', 'Greens', 'Oranges', 'Reds'])
```

- **Figure size**: Use nature figure width (18 cm (180 mm), page wide) for a two-column figure, and 9 cm (90 mm) width for a one-column figure:

```python
fw = 9*cm # one-column width
fh = 0.75 * fw # usual aspect ratio
```

- **Composite figures**: Most of the times, the final figure imported to overleaf should have a figure width of $width = 2*fw$. We always want to avoid overlapping text, and overcrowding the figure.

- **font sizes**: Typically we use the standard font sizes below, but for composite figures with many sub-panels, we can use the "tiny-subpanel" font sizes for small sub-panels.

```python
##### Standard figure font size

plt.rcParams["font.size"] = 8
plt.rcParams["axes.labelsize"] = 8
plt.rcParams["xtick.labelsize"] = 6
plt.rcParams["ytick.labelsize"] = 6
```
```python
##### Tiny sub-panel font size

plt.rcParams["font.size"] = 6.5
plt.rcParams["axes.labelsize"] = 6.5
plt.rcParams["xtick.labelsize"] = 6.0
plt.rcParams["ytick.labelsize"] = 6.0
```
